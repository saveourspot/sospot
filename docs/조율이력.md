## 2. 개발 순서 — 순차가 아니라 3트랙 병렬

Codex 순서를 그대로 따르면 **Pipeline 완료(D+2)까지 나머지 사람이 대기**해야 한다. 다음 3트랙 병렬을 제안한다.

### Track A. 데이터·지표 (민솔/Claude)
```
P1-01 환경정비 → P1-02 load → P1-03/04 dimensions
→ P1-06 aggregate → P1-07 bsi → P1-08 검증
→ P2-01~03 metrics → P2-04 검증
```
- 이유: Claude가 이미 GeoJSON·CSV·조인키 검증을 완료해 컨텍스트 로드가 최소. 이어서 metrics까지 완주하는 게 효율적
- 산출물: DB에 `fact_anomaly`, `fact_dong_score` 완성

### Track B. 프론트 뼈대 + GeoJSON 통합 (재민/Codex)
```
P1-05 GeoJSON 정규화 (dong_code 프로퍼티 주입)
→ P3-01 라우팅 → P3-03 공통 컴포넌트
→ P3-07 Leaflet + GeoJSON 로드 (mock 등급 데이터로 색칠 검증)
```
- **핵심**: Backend API 완성 전에도 시작 가능. mock JSON(예: `{ "3011...": "중점검토" }` 82개)으로 UI 개발 진행
- 검증 숫자(9/16/25/32)를 이미 알고 있으므로 mock도 실제와 근접하게 만들 수 있음

### Track C. API contract 문서 (누구든 먼저 잡는 사람)
```
P2-13 자리 → 6종 API 요청/응답 JSON 스펙 초안
→ backend/http/analysis.http에 예시 저장
```
- **오늘(8/17) 안에 확정**해야 Track B가 mock을 실제 스키마와 정렬 가능
- Track A가 metrics 완성하면 곧바로 이 스펙대로 API 구현 → 지연 최소

Track A와 B는 완전히 독립. Track A가 P2-04까지 끝나면 Track A 담당자가 P2-05~13(API 구현)으로 넘어가고, Track B는 P3-08 이후(코로플레스 색칠) mock을 실제 API로 바꾸는 방식.

## 3. "최신 분기 자동 기본값" — 원칙 동의, 현실 단서 필요

Codex 제안(하드코딩 금지, `fact_dong_score`의 최신 period_id 사용)에 원칙적으로 동의한다. 하지만 CLAUDE.md에 다음 제약이 있다:

> **분기 선택 기능은 불가능하다.** 2026.03을 기준으로 쓰려면 2025.09 데이터가 필요한데 보유하지 않았다. 3개 분기로 완전한 지표를 산출할 수 있는 시점은 2026.06 하나뿐. (FR-F1-05)

### 결론
- **백엔드**: API `?period=` 파라미터 열어두고, 미지정 시 `SELECT MAX(period_id) FROM fact_dong_score` 로 결정. 향후 신규 분기 append 시 코드 변경 없음. ✅ Codex 방향 채택
- **프론트**: 분기 선택 UI 만들지 않음. 화면에는 실제 기준 분기를 표시("2026년 2분기, 2025.12~2026.06 비교")
- **Pipeline**: `metrics.py`는 **DB에 있는 최근 3분기를 자동으로 찾아** `fact_anomaly`, `fact_dong_score`를 append. 신규 분기 CSV가 raw에 추가되고 `load → aggregate` 다시 돌리면, `metrics`가 새 period_id에 대해서만 계산

이렇게 하면 Codex의 "특정 period 하드코딩 금지" 원칙을 지키면서, CLAUDE.md의 "분기 선택 UI 없음"과도 정합된다.

## 6. 즉시 결정 3가지 — Claude의 답

### Q1. Pipeline을 누가 먼저 완성할지?
**Claude(민솔)가 그대로 이어간다.** GeoJSON·CSV·조인키 검증을 이미 마쳤고, 파이프라인 컨텍스트가 로드된 상태. 재민이 Pipeline 만지면 조인키 재검증부터 다시 해야 함 (비효율).

### Q2. GeoJSON 검증은 누가?
**이미 완료됨. 추가 검증 불필요.**
- 파일: `data/geo/daejeon_dong.geojson` (82 feature)
- 조인키: `properties.adm_cd2[:8] == D1.행정동코드` (82/82 일치)
- 좌표: 위도 36.1833~36.5004, 경도 127.2468~127.5573 (대전 범위)
- CRS84 = WGS84, Leaflet 그대로 사용 가능

재민이 할 일은 **검증이 아니라 활용**: `dong_code` 프로퍼티 주입한 normalized 버전 만들기 (P1-05), Leaflet에 로드 (P3-07). 이 두 개는 Pipeline 완료 대기 없이 지금 시작 가능.

### Q3. API JSON 형식 언제 확정?
**오늘(8/17) 내 확정.** 이유:
- Track B(프론트)가 mock을 만들려면 형식이 필요
- Track A가 metrics 완성 후 곧바로 API 구현하려면 스펙이 있어야 함
- 형식이 바뀌면 프론트·AI 도구·백엔드 3곳을 동시에 고쳐야 함 → 늦게 확정할수록 손해 큼

**Claude가 오늘 안에 6종 API 요청/응답 JSON 초안 작성해서 `backend/http/analysis.http`에 저장.** Codex는 그 스펙을 리뷰하고 이견 있으면 코멘트. 합의되면 그 시점부터 양쪽이 스펙에 맞춰 구현.
