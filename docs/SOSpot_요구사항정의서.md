> 작성일 2026-08-14 · 팀 SOSpot(2인) · 데이터 보유기관: 소상공인시장진흥공단

## 1. 핵심 개요

### 1.1 문제 정의
정책 담당자가 "어느 지역을 먼저 봐야 하는가"를 판단하려면 여러 분기·지역·업종을 수작업으로 교차 비교해야 한다. 특히 **전반적 경기 흐름으로 인한 변화**와 **특정 지역에서만 나타나는 부진**을 구분하기 어렵다.

> **실데이터 검증 결과 이 문제는 더 뚜렷해졌다.** 대전 전체 점포수는 최근 분기에 오히려 **증가**했고(78,246 → 78,607 → 80,704), 74개 업종 중 53개가 증가세다. 즉 "감소한 곳을 찾는" 단순 접근으로는 대상 지역을 거의 못 찾는다. **전체가 오르는데 여기만 안 오르는 곳**을 찾아야 한다.

### 1.2 한 줄 정의
> 분기별 상가정보를 행정동×업종 단위로 집계·비교하여, **대전 전체 추세 대비 상대적으로 부진한 지역**을 자동 탐지하고 그 근거를 자연어로 설명하는 웹 서비스.

### 1.3 성공 기준
| ID | 기준 | 검증 결과 |
|---|---|---|
| C1 | 대전 전 행정동 커버 | **달성 가능** — 82개 행정동, 결측 0건 |
| C2 | 3개 분기 시계열 확보 | **확보 완료** — 2025.12 / 2026.03 / 2026.06 |
| C3 | 모든 판정에 수치 근거 3종 동반 | 설계 반영 |
| C4 | 테스트 질의 30개 도구·파라미터 매핑 정확도 90% | 개발 후 측정 |
| C5 | 분석 API 2초 / AI 응답 10초 이내 | 성능 목표로 설정, 개발 후 측정. 주요 분석 조합 5,067개, 전체 집계 약 1.8만 행 규모 |

### 1.4 설계 원칙
1. **집계 단위로만 비교한다** — 개별 점포 폐업을 추정하지 않는다 (근거는 5.3 DC-1).
2. **모든 판정에 근거를 붙인다** — 규칙 기반 지표로 "왜 이 지역인가"를 항상 설명한다.
3. **AI는 수치를 지어내지 않는다** — LLM은 질의 해석과 서술만, 숫자는 분석 API 결과에서만.

## 2. 사용자 정의

### 2.1 페르소나 1 (Primary) — 정책 담당 주무관
- 대전시청/자치구 소상공인 정책 부서, 데이터 분석 비전문가
- **업무 맥락**: 분기마다 지원사업 대상 지역을 선정해야 하는데, 근거 자료를 만들려면 엑셀로 직접 돌려야 함
- **필요**: "이번 분기 우선 검토할 지역 5곳과 그 이유"를 10분 안에
- **좌절 지점**: 어디가 *유독* 나쁜지 판단할 기준이 없음

### 2.2 페르소나 2 (Secondary) — 소상공인지원센터 상담사
- **필요**: 특정 행정동/업종의 최근 흐름과 대전 전체 대비 위치를 빠르게 확인

## 3. 사용자 플로우

### 3.1 메인 플로우 (핵심 시나리오)

```
[F0] 랜딩/메인
      │  "이번 분기 대전 상권, 어디를 봐야 하나"
      ▼
[F1] 이상징후 지도  ◀─────────────┐
      │  지도에서 중점검토 지역 발견 │
      ▼                          │
[F2] 행정동 상세 패널             │ (지도로 복귀)
      │  "왜 이 지역인가" 근거 확인 │
      ├──────────────┐           │
      ▼              ▼           │
[F3] 업종 분석      [F4] 지역 비교 │
      │              │           │
      └──────┬───────┘           │
             ▼                   │
   결과 CSV 내보내기 (FR-C-05) ──┘

  ※ [F6] AI 질의응답은 모든 화면에서 진입 가능 (사이드 패널)
     AI 답변 내 지역명 클릭 → [F2]로 이동
  ※ 검토 목록(구 F5)은 범위에서 제외 — 8.5 참조
```

### 3.2 보조 플로우
- **AI 우선 진입**: F0 → F6(질문 입력) → 답변 + 근거 표 → F2
- **탐색형 진입**: F0 → F3(업종 먼저 선택) → 해당 업종의 이상징후 지역 목록 → F2

### 3.3 플로우 설계 근거
정책 담당자의 업무 순서를 **발견 → 원인 확인 → 비교 → 선별**로 가정했다. 이는 서비스 목적과 업무 환경으로부터 도출한 가정이며 실사용자 인터뷰로 검증한 것은 아니다. 화면 구성을 이 순서에 그대로 맞추고, AI는 별도 메뉴가 아니라 어느 단계에서든 끼어들 수 있는 보조 채널로 둔다. AI를 독립 메뉴로 빼면 "챗봇을 얹은 대시보드"로 보이지만, 플로우에 녹이면 **같은 분석 결과에 도달하는 두 번째 경로**가 된다.

## 4. 화면별 기능 요구사항

우선순위: **M**(필수·MVP) / **S**(중요) / **C**(여유 시)

> 개별 FR의 우선순위는 8.5 화면 단위 범위 조정과 일치한다. 8.5에서 '여유 시'로 분류된 화면(F3·F4)의 FR은 화면 안에서 아무리 핵심이어도 **M을 부여하지 않는다.** 화면 자체가 잘릴 수 있기 때문이다.

### F0. 메인 페이지

**목적**: 3초 안에 "이 서비스가 무엇을 알려주는지" 전달하고 지도로 보낸다.

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-F0-01 | 서비스 한 줄 정의와 기준 분기(예: 2026년 2분기) 표시 | M |
| FR-F0-02 | 이번 분기 요약 지표 카드 4종: 분석 대상 행정동 수 / 중점검토·주의 지역 수 / 대전 전체 점포 증감률 / 대전 체감 BSI | M |
| FR-F0-03 | "이번 분기 우선검토 지역 TOP 5" 카드 — 클릭 시 F2로 직행 | M |
| FR-F0-04 | 메인 CTA "이상징후 지도 보기" → F1 | M |
| FR-F0-05 | AI 질의 입력창을 메인에 노출 + 추천 질문 3개 프리셋 | S |
| FR-F0-06 | 데이터 출처·기준일자·갱신 시점 상시 표기 | M |
| FR-F0-07 | 지표 산출 방식 설명 페이지 링크 (계산식·표본 하한 공개) | S |

> BSI 사용처는 FR-F0-02 요약 카드와 FR-F2-04 추세 차트 배경 두 곳이다. 근거는 5.1-1 참조.

### F1. 이상징후 지도

**목적**: 대전 전역을 한 화면에서 훑고 볼 곳을 고른다.

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-F1-01 | 82개 행정동 경계 코로플레스, 종합 등급별 4색 표시(중점검토/주의/관심/정상) | M |
| FR-F1-02 | **기본 레이어는 업종 대분류 기준** — 82개 행정동 전부 등급 산출 가능 | M |
| FR-F1-03 | 업종 필터: 대분류 10종 선택 시 해당 업종만의 등급으로 지도 갱신 | M |

| FR-F1-05 | 기준 분기는 **2026.06 고정** — 화면 상단에 기준 분기와 비교 구간(2025.12~2026.06) 명시 | M |
| FR-F1-06 | 지도 우측에 등급순 행정동 리스트 병렬 표시, 지도↔리스트 양방향 하이라이트 | M |

### F2. 행정동 상세 패널

**목적**: "왜 이 지역인가"에 답한다. **이 화면이 서비스의 심장이다.**

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-F2-01 | 헤더: 행정동명·자치구·종합 등급·점수·대전 내 순위 | M |
| FR-F2-02 | **판정 근거 요약문 자동 생성** (예: "최근 2분기 연속 감소한 업종 3개, 대전 평균 대비 상대격차 -8.2%p") | M |
| FR-F2-03 | 이상 업종 TOP 3 카드 — 업종명, 점포수 3분기 추이, 지역 증감률, 대전 증감률, 상대격차 | M |
| FR-F2-04 | 지역 vs 대전 전체 추세 비교 라인차트 (같은 축에 2개 선) + 배경에 분기별 대전 체감 BSI 밴드 | M |
| FR-F2-05 | 업종별 상대격차 바차트 (음수 왼쪽/양수 오른쪽 발산형) | M |

| FR-F2-07 | "이 업종 자세히" → F3 / "다른 지역과 비교" → F4 | M |

### F3. 업종 분석 — *전체 S/C (8.5 '여유 시')*

**목적**: 대분류에서 잡힌 신호를 중분류로 좁혀 원인을 특정한다.

> **F3는 진입 컨텍스트에 따라 두 모드로 동작한다.** 행정동이 선택된 상태로 진입하면(F2 → F3) 해당 지역의 세부 업종을 분석하고, 업종만 선택된 상태로 진입하면(F0 → F3) 해당 업종의 대전 전체 지역 분포를 분석한다. 화면은 하나이며 상단 컨텍스트 배지로 현재 모드를 표시한다.

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-F3-01 | 선택 대분류 하위 중분류별 점포수 추이·증감률 테이블 | S |
| FR-F3-02 | 중분류별 상대격차 정렬 및 이상 표시 | S |
| FR-F3-03 | 표본 하한 미달 중분류는 회색 처리 + 사유 툴팁 | S |
| FR-F3-04 | 해당 중분류의 대전 전체 상위 이상징후 지역 목록 (교차 탐색) | C |
| FR-F3-05 | 업종 단위로 지도 재진입 (F1에 필터 적용된 상태로) | C |

### 5.1-1 BSI의 역할 — 장식이 아니라 방법론의 근거

분기 평균으로 집계한 대전 체감 BSI와 대전 총 점포수를 나란히 놓으면 다음과 같다.

| 분기 | 대전 체감 BSI | 대전 총 점포수 | 점포수 증감 |
|---|---|---|---|
| 2025Q4 | 72.7 | 78,246 | — |
| 2026Q1 | 65.2 | 78,607 | +0.46% |
| 2026Q2 | **60.0** | 80,704 | +2.67% |

> 2026Q2 체감 BSI는 **6월 체감값 결측으로 4~5월 확정값 평균**이다. 화면에도 기준월을 함께 표기한다.

**체감경기는 계속 나빠지는데(72.7 → 60.0, 전 구간 100 미만) 점포수는 오히려 늘었다.**

이 한 장의 표가 SOSpot의 존재 이유를 증명한다. 점포수 총량만 보면 대전 상권은 개선 중으로 읽히지만, 현장 체감은 반대 방향이다. 따라서 **총량 증감이 아니라 대전 전체 추세 대비 상대격차로 봐야 한다**는 것이 방법론의 출발점이 된다.

BSI는 지역×업종 교차가 불가능해 지표 계산에 결합할 수 없지만, **왜 상대격차 방식을 택했는가에 대한 근거 데이터**로서 서비스의 논리를 떠받친다. 화면에서는 메인 요약 카드와 지역 상세 추세 차트 배경 두 곳에서 쓰인다.

## 6. 이상징후 탐지 로직 명세

### 6.1 정의
행정동 `d`, 업종 `c`, 분기 `t`의 점포수 `N(d,c,t)`에 대해:

```
증감률      g   = (N_t − N_{t−1}) / N_{t−1}
대전 전체   G   = (ΣN_대전(c,t) − ΣN_대전(c,t−1)) / ΣN_대전(c,t−1)
상대격차    RD  = g − G
누적변화율  CUM = (N_t − N_{t−2}) / N_{t−2}
연속감소    C   = 1 if g(t) < 0 and g(t−1) < 0 else 0
```

### 6.2 점수
```
전제: N_{t−2} ≥ 20   (미만은 sample_size_flag = LOW, 등급 산정 제외)

P_rd  = 대전 내 전체 조합에서 (−RD)의 백분위 (0~100)
P_cum = 대전 내 전체 조합에서 (−CUM)의 백분위 (0~100)

Score = 0.5 × P_rd + 0.3 × P_cum + 0.2 × (C × 100)

등급: ≥80 중점검토 / 65~80 주의 / 50~65 관심 / <50 정상
```

> **등급 명칭 확정**: `정상 / 관심 / 주의 / 중점검토`. '심각·경계'는 재난 용어에 가까워, 점포수 스냅샷 변화를 다루는 이 서비스에는 과하다. 최상위 등급을 **중점검토**로 두면 서비스 목적(우선검토 후보 선별)과 등급명이 일치한다. 문서·화면·API 응답 전부 이 4개 명칭만 사용한다.

> **등급은 절대 기준이 아니라 대전 내 상대 순위다.** 백분위 기반이므로 대전 전체가 좋아져도 하위권은 항상 존재한다. UI에 "대전 내 상대적 위치"임을 명시해 오해를 막는다.

### 6.3 행정동 종합 등급

```
이상업종수(d) = 표본 하한을 충족하면서 업종 Score ≥ 50(관심 이상)인 대분류 업종의 수

Raw(d)  = 상위 min(3, 유효조합수)개 업종 Score 평균 × min(1.0, 0.6 + 0.1 × 이상업종수)
Pct(d)  = 대전 82개 행정동 내 Raw의 백분위 (0~100)

등급: Pct ≥ 90 중점검토 / 70~90 주의 / 40~70 관심 / <40 정상
```

> **왜 행정동 단위에서 백분위를 다시 계산하는가**: 조합 단위 Score를 행정동 단위로 집계하면 값의 분포가 중앙으로 압축되므로, 조합 단위의 절대 임계값(6.2의 80/65/50)을 그대로 적용하기 어렵다. 이에 **행정동 간 우선검토 순위 제공**이라는 서비스 목적에 맞춰 Raw 점수를 82개 행정동 내 백분위로 변환한다. 이 등급은 위험도의 절대값이 아니라 **대전 내 상대적 검토 우선순위**를 의미하며, 순위는 그대로 보존되므로 탐지 결과 자체는 바뀌지 않는다.

> 행정동별 유효 대분류 조합 수는 평균 7.4개(최소 2, 최대 10)다. **동구 대청동만 2개**이므로 상위 3개를 고정 참조하면 오류가 난다. 유효 조합 수가 3 미만이면 있는 만큼만 평균 내고, 화면에 '표본 제한' 배지를 표시한다.

**행정동 종합 상위 (중점검토 9곳)**: 중구 목동 · 중구 대흥동 · 유성구 온천2동 · 서구 복수동 · 서구 둔산3동 · 동구 삼성동 · 동구 가양2동 · 중구 유천2동 · 중구 문창동 — 서구 도안동은 '주의'로 그 다음 순위다.

> 기획서에 예시로 적은 "온천2동", "도안동"이 실제 상위권에 들어왔다. 데모 시나리오를 그대로 쓸 수 있다.

**목동 사례가 이 서비스의 가치를 그대로 보여준다.** 음식업 117개는 여전히 많고 감소폭도 −3.3%로 작아서 단순 조회로는 전혀 눈에 띄지 않는다. 하지만 대전 전체 음식업이 +3.0% 성장하는 동안 혼자 줄었다. 이게 상대격차 방식이 아니면 못 잡는 신호다.

### 6.4-1 백분위 산출 방식 비교 검증

`P_rd`와 `P_cum`을 어느 모집단에서 계산할지에 두 가지 선택지가 있어 실데이터로 비교했다.

| 방식 | 설명 |
|---|---|
| **A안 (채택)** | 604개 조합 **전체 풀**에서 백분위 산출 |
| B안 | **업종별로** 82개 행정동 안에서 백분위 산출 |

**비교 결과**

| 항목 | 값 |
|---|---|
| 전체 순위 상관 (Spearman) | **0.960** |
| 상위 10개 조합 일치 | **8 / 10** |

업종별 상대격차 표준편차는 음식 0.028 ~ 숙박 0.219로 8배 차이가 나므로 B안이 이론적으로 더 정교하다. 그러나 **두 방식의 순위가 사실상 같고**, 숙박(유효 조합 11개)·보건의료(32개)처럼 표본이 작은 업종에서 B안은 "11개 중 1위 = 100점"이 되어 과대평가 위험이 있다.

**A안을 채택하되, 이 비교 자체를 문서에 남긴다.** 방법론 선택이 결과를 좌우하지 않음을 확인한 것이 심사 대응에서 더 가치 있다.

### 6.5 근거 데이터 (모든 판정에 필수 동반)
- 이상 업종 TOP 3와 각각의 `N` 3분기 추이, `g`, `G`, `RD`
- 대전 전체 대비 백분위
- 해당 시점 대전 체감 BSI (배경 정보이며 판정 미반영임을 UI에 명시)

## 7. AI 질의응답 설계

### 7.1 방식: Tool Calling
대시보드와 AI가 **동일한 분석 API**를 호출하므로 두 화면의 숫자가 항상 일치한다. Text-to-SQL은 이상징후 정의를 LLM이 임의로 재해석할 위험이 있어 배제.

### 7.2 도구 정의
| 도구 | 파라미터 | 대응 질의 | 우선 |
|---|---|---|---|
| `searchAnomalyRegions` | period, catCode?, catLevel, grade?, **consecutiveDecline?**, **sortBy?**, topN | "최근 소매업이 계속 줄어든 지역은?" | M |
| `getRegionDetail` | dongCode, period | "온천2동이 왜 중점검토야?" | M |
| `compareRegions` | dongA, dongB, period, catCode? | "도안동과 온천2동 비교해줘" | M |
| `getCategoryTrend` | catCode, periodRange, scope | "대전 전체 음식업 추세는?" | S |
| `getBsiContext` | periodMonth | "요즘 대전 소상공인 체감경기 어때?" | C |

> `sortBy`는 `score` / `relativeGap` / `cumChange` 세 값만 허용한다. `consecutiveDecline`이 있어야 "계속 줄어든"이라는 표현을 조건으로 변환할 수 있고, `sortBy`가 있어야 "가장 많이 줄어든" 같은 질의를 커버한다. 임의 필드 정렬을 허용하면 Tool Calling의 안전성이 무너지므로 열거값으로 제한한다.

### 7.3 처리 흐름
```
질문 → LLM(도구 선택 + 파라미터 추출)
     → 명칭 정규화 (별칭 사전: "온천2동"→행정동코드, "식당"→I2 음식)
     → 분석 API 실행
     → 결과 JSON을 LLM에 전달 → 서술형 답변 생성
     → 답변 + 근거 표/차트 렌더링
```

### 7.4 가드레일
- 도구 결과에 없는 수치 생성 절대 금지 (시스템 프롬프트 명시)
- 결과 0건 → 고정 안내 응답
- 대전 외 지역 / 보유 분기 밖 기간 → 범위 안내
- 표본 부족 조합 질의 → "판정 제외 사유" 설명
- LLM API 키는 서버 측 보관

### 7.5 별칭 사전 (구축 필요)
- 행정동: 82개 정식명 + 축약형("온천2", "둔산3")
- 업종: 대분류 10개 + 중분류 74개 정식명 + 구어체("식당"→음식, "카페"→비알코올, "학원"→교육)

## 8. 아키텍처 및 진행 방향

### 8.1 구성
```
[공공데이터포털 CSV]  분기 1회 수동 다운로드
        ▼
[전처리·집계 배치]  Python + pandas  (오프라인, 상시 실행 불필요)
        ▼
[PostgreSQL]  집계·지표 테이블 (원본 CSV 미적재)
        ▲ JPA
[Spring Boot API]  분석 API + LLM 오케스트레이터
        ▼ REST
[React]  지도(코로플레스) + 차트 + AI 사이드 패널
```

**데이터 규모 근거**: 원본 3분기 24만 행(약 126MB)을 집계하면 `fact_store_count`는 대분류 807 + 중분류 5,067 = 분기당 약 5,900행. 3분기 전체 **1.8만 행**. 인덱스 없이도 즉시 응답한다.
