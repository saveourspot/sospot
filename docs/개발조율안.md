# SOSpot 개발 조율안

> 최종 확정일: 2026-08-17  
> 목적: Claude와 Codex가 병렬 개발할 때 산식, DB, API, 데이터 조인, Frontend 동작이 서로 어긋나지 않도록 공통 기준을 정의한다.

---

## 1. 개발 기본 원칙

SOSpot은 대전 소상공인 상권 데이터를 이용하여
행정동 × 업종 단위의 최근 변화를 분석하고,
대전 전체 동일 업종과 비교해 상대적으로 이상징후가 큰 지역을 찾는 서비스다.

SOSpot은 다음을 수행하지 않는다.

- 개별 점포 폐업 판정
- 폐업률 계산
- 미래 폐업 예측
- 미래 매출 예측
- 정책지원 대상 자동 결정

서비스 전체에서 다음 표현을 사용한다.

- 점포 수 변화
- 이상징후
- 상대격차
- 검토 우선순위
- 정상
- 관심
- 주의
- 중점검토
- 표본 부족
- 판정 제외

다음 표현은 사용하지 않는다.

- 폐업률
- 폐업 위험도
- 폐업 확률
- 미래 폐업 가능성
- AI 위험 예측

---

# 2. 확정된 공통 규약

Claude와 Codex는 다음 6개 규약을 임의로 변경하지 않는다.

변경 필요성이 발생하면 먼저 팀원 간 조율한 후 문서를 수정한다.

## 2.1 분석 산식

행정동 `d`, 업종 `c`, 기준 분기 `t`에 대해:

```text
g =
(N_t - N_t-1) / N_t-1

G =
(대전전체_N_t - 대전전체_N_t-1)
/
대전전체_N_t-1

RD = g - G

CUM =
(N_t - N_t-2) / N_t-2

C = 1
if 두 연속 구간 모두 감소
else 0
```

표본 하한:

```text
N_t-2 >= 20
```

표본 하한을 만족하는 조합에 대해:

```text
P_rd  = (-RD)의 전체 유효 조합 내 percentile
P_cum = (-CUM)의 전체 유효 조합 내 percentile
```

Score:

```text
Score =
0.5 * P_rd
+ 0.3 * P_cum
+ 0.2 * (C * 100)
```

업종 등급:

```text
Score >= 80
→ 중점검토

65 <= Score < 80
→ 주의

50 <= Score < 65
→ 관심

Score < 50
→ 정상
```

행정동 종합:

```text
anomaly_cat_count =
표본 하한 충족 AND Score >= 50인 대분류 업종 수
```

```text
Raw(d) =
상위 min(3, 유효 업종 수) Score 평균
*
min(1.0, 0.6 + 0.1 * anomaly_cat_count)
```

```text
Pct(d) =
82개 행정동 내 Raw percentile
```

행정동 등급:

```text
Pct >= 90
→ 중점검토

70 <= Pct < 90
→ 주의

40 <= Pct < 70
→ 관심

Pct < 40
→ 정상
```

가중치, 표본 하한, 등급 임계값을 임의로 변경하지 않는다.

## 2.2 DB Schema

Flyway V1~V3 기준 구조를 유지한다.

주요 테이블:

```text

dim_category

fact_store_count
fact_anomaly
fact_dong_score
fact_bsi

```

이미 적용된 Flyway migration은 임의로 수정하지 않는다.

Schema 변경이 필요하면:

```text
V4__
V5__
...
```

형태의 신규 migration을 생성한다.

DataGrip에서 직접 DDL을 실행하여
프로젝트 schema를 변경하지 않는다.

## 2.3 API Contract

Frontend, Backend, AI Tool은 동일한 API contract를 사용한다.

API contract는 Backend 구현보다 먼저 확정한다.

현재 기준 API는 총 7종이다.

```text
GET /api/summary

GET /api/regions/scores

GET /api/anomaly/regions

GET /api/regions/{dongCode}

GET /api/regions/compare

GET /api/categories/{catCode}/trend

GET /api/bsi
```

AI Tool은 이 API를 기반으로 구성한다.

API contract가 확정된 이후에는
Frontend와 Backend 어느 한쪽에서 임의로 필드명을 변경하지 않는다.

변경 필요 시 양쪽이 먼저 합의한다.

---

## 2.4 최신 분기 결정

특정 period를 코드에 하드코딩하지 않는다.

예:

```text
202606
```

을 Backend나 Frontend의 기본값으로 직접 넣지 않는다.

Backend에서 `period`가 생략되면
분석이 완료된 가장 최신 분기를 사용한다.

기본 기준:

```sql
SELECT MAX(period_id)
FROM fact_dong_score;
```

현재 데이터에서는 결과적으로:

```text
202606
```

이 선택되지만,
향후 신규 분기 분석 결과가 추가되면
코드 변경 없이 최신 분기로 이동해야 한다.

---

## 2.5 GeoJSON Join Key

상권정보와 GeoJSON의 기본 조인키:

```text
dong_code
```

GeoJSON 원본의 경우:

```text
dong_code = adm_cd2[:8]
```

을 사용한다.

검증 완료:

```text
대전 행정동 82개
GeoJSON 82 feature
82 / 82 완전 매칭
```

Frontend에서도 행정동명보다 `dong_code`를 우선 사용한다.

행정동명 문자열을 주 join key로 사용하지 않는다.

# 3. API 공통 Response 형식

7종 API의 기본 response envelope를 통일한다.

기본 형태:

```json
{
  "period": "202606",
  "data": {}
}
```

3개 비교 분기가 필요한 API:

```json
{
  "period": "202606",
  "comparisonPeriods": [
    "202512",
    "202603",
    "202606"
  ],
  "data": {}
}
```

Frontend는 `period`를 자체적으로 추측하거나 하드코딩하지 않는다.

화면에 표시할 기준 분기는
Backend 응답의 `period`를 사용한다.

# 5. F1 지도 데이터 규칙

지도는 두 가지 모드로 구분한다.

## 5.1 업종 필터 없음

행정동 종합 결과 사용:

```text
fact_dong_score
```

API:

```text
GET /api/regions/scores
```

82개 행정동 각각에 대해
종합 등급과 Score를 반환한다.

Frontend는 이를 이용하여
행정동 Polygon을 색칠한다.

---

## 5.2 특정 업종 선택

해당 업종 조합 결과 사용:

```text
fact_anomaly
```

예:

```text
음식업 선택
```

시:

```text
행정동 × 음식업
```

결과를 조회한다.

Frontend에서 점수나 등급을 다시 계산하지 않는다.

Backend가 반환한 결과를 그대로 사용하여 색상만 갱신한다.

업종을 선택한 경우에는 선택 업종만을 대상으로 기존 행정동 종합 산식을
다시 적용하여 82개 행정동의 상대적인 검토 우선순위를 표시한다.

- 지도 진입 시 대분류 10개 업종을 전체 선택한 상태를 기본값으로 사용한다.
- `전체 업종` 선택 항목은 10개 업종 전체 선택과 전체 해제를 전환한다.
- 선택 업종이 0개이면 지도 등급 색상과 분석 목록을 표시하지 않는다.
- `sample_size_flag = LOW`인 표본 부족 업종은 계산에서 제외한다.
- 선택 업종이 모두 표본 부족이면 해당 행정동은 `판정 제외`로 표시한다.
- 유효한 선택 업종 중 Score 상위 최대 3개 평균과 이상업종 수 보정을 사용한다.
- 같은 선택 조건으로 계산한 Raw 값을 82개 행정동끼리 비교해 percentile을 계산한다.
- 등급은 기존 행정동 종합 percentile 임계값을 적용한다.
- 대분류 10개를 모두 선택하면 기존 `fact_dong_score` 결과와 동일해야 한다.
- 이 값은 `fact_dong_score`의 행정동 종합 Score와 구분하여
  `선택 업종 검토 우선순위`로 표시한다.
- Score와 등급은 Backend가 계산하며 Frontend에서 재계산하지 않는다.

## 5.3 금지

Frontend에서 다음 계산을 수행하지 않는다.

```text
Score 계산
percentile 계산
grade 계산
행정동 종합 Score 계산
```

모든 분석은 Pipeline에서 완료되어 DB에 저장된 결과를 사용한다.

행정동 상세의 성장 모멘텀은 저장된 업종별 점포 수 변화와 상대격차를 이용해
Backend에서 `지속 성장형`, `회복 전환형`, `상대 우위형`, `최근 증가형`으로
분류한다. 함께 제공하는 정책 검토 방향은 자동 정책 결정이나 효과 예측이 아니라
현장 자료로 추가 확인할 체크리스트이며, Frontend와 AI는 동일한 API 결과를 사용한다.

# 6. 신규 분기 처리

신규 분기 상가정보가 추가될 수 있다는 전제로 구현한다.

현재:

```text
202512
→ 202603
→ 202606
```

향후:

```text
202609
```

가 추가되면 신규 분석은:

```text
202603
→ 202606
→ 202609
```

을 사용한다.

Pipeline 흐름:

```text
신규 Raw CSV
↓
load
↓
aggregate
↓
fact_store_count append
↓
최근 연속 3개 분기 확인
↓
metrics
↓
fact_anomaly append
↓
fact_dong_score append
```

기존 분석 결과는 삭제하거나 재계산하지 않는다.

예:

```text
202606 분석 결과
```

는 그대로 유지한다.

신규 분석 결과만:

```text
202609
```

로 추가한다.

분기별 결과는 snapshot 개념으로 보존한다.

# 8. GeoJSON 처리

GeoJSON은 수동으로 직접 편집하지 않는다.

재현 가능한 script를 통해 normalized GeoJSON을 생성한다.

예:

```text
원본 GeoJSON
↓
대전 feature 필터
↓
adm_cd2[:8]
↓
dong_code 생성
↓
validation
↓
normalized GeoJSON 생성
```

검증 항목:

```text
feature count = 82
dong_code unique count = 82
duplicate 없음
누락 없음
상권정보 행정동 코드와 82/82 매칭
```

예상 산출물:

```text
data/geo/daejeon_dong.geojson
```

Frontend에서는 normalized GeoJSON을 사용한다.

# 9. Frontend Mock 정책

Backend API 완성 전에도
Frontend 개발을 진행하기 위해 mock data 사용을 허용한다.

단, mock은 반드시 API contract와 동일한 구조를 사용한다.

예:

```text
mockRegionScores.js
```

mock 파일에는 다음 의미를 명확히 한다.

```text
Contract/UI development fixture.
Not actual analysis output.
```

Mock data는 실제 분석 결과로 취급하지 않는다.

Backend API가 준비되는 즉시
mock을 실제 API 연결로 교체한다.

Frontend 비즈니스 로직이
mock 데이터 구조에 종속되지 않도록 한다.

# 14. AI 장애 Fallback

시연용 AI 응답을 하드코딩하지 않는다.

잘못된 방식:

```text
질문 A
→ 미리 작성한 답변 A

질문 B
→ 미리 작성한 답변 B
```

대신 LLM 호출 실패 시에도
실제 Backend API 결과를 사용한다.

정상:

```text
Backend API
↓
실제 DB 데이터
↓
LLM
↓
자연어 답변
```

Fallback:

```text
Backend API
↓
실제 DB 데이터
↓
deterministic template
↓
자연어 답변
```

즉 분석 데이터 자체는 항상 실제 결과를 사용한다.

LLM 장애 시 자연어 표현 단계만 template 방식으로 대체한다.

# 15. Git 작업 규칙

각 Track은 별도 feature branch에서 작업한다.

예:

```text
feat/pipeline-metrics
feat/backend-summary-api

feat/geo-normalize

feat/frontend-map
```

작업 완료 후:

```text
branch
↓
push
↓
Pull Request
↓
review
↓
main merge
```

main에서 직접 기능 개발하지 않는다.

# 16. 작업 상태 관리

`docs/작업계획.md`는
개발 방향과 task 정의의 기준 문서로 사용한다.

단, 매 작업 시작/종료 때마다
동일 문서의 상태를 수정하여 commit하는 방식은 사용하지 않는다.

이유:

두 개발자가 동시에 작업할 경우
코드와 무관하게 `작업계획.md`에서 Git conflict가 발생할 수 있다.

실시간 작업 상태는 다음 중 하나를 사용한다.

우선:

```text
GitHub Branch
+
Pull Request
```

필요 시:

```text
GitHub Issues / Projects
```

를 추가한다.

예:

```text
feat/p3-07-leaflet
```

브랜치가 존재하면 해당 작업이 진행 중임을 알 수 있다.

`작업계획.md`는 계획 자체가 변경될 때만 수정한다.

# 17. 실무 문서 관리

현재 유효한 문서와
과거 조율 이력을 분리한다.

권장:

```text
docs/
├─ 작업계획.md
├─ 개발조율안.md
└─ 조율이력.md
```

### 작업계획.md

현재 실제 task와 개발 순서.

### 개발조율안.md

Claude와 Codex가 공통으로 따라야 하는
현재 확정 규칙.

### 조율이력.md

과거 Claude/Codex 의견 교환 기록.

AI agent가 작업할 때는 기본적으로:

```text
작업계획.md
개발조율안.md
```

만 현재 기준으로 사용한다.

`조율이력.md`는
현재 요구사항 판단 근거로 사용하지 않는다.

# 23. 현재 최종 합의

다음 사항은 합의 완료 상태로 간주한다.

- Track A / Track B 병렬 개발
- Claude = Pipeline → Backend
- Codex = GeoJSON → Frontend
- API Contract 선확정
- API 7종
- API response envelope 통일
- `period` optional
- 최신 분석 완료 분기 자동 사용
- Frontend period 하드코딩 금지
- 현재 MVP 분기 선택 UI 미구현
- 기본 지도 = `fact_dong_score`
- 업종 필터 지도 = `fact_anomaly`
- Frontend Score/grade 재계산 금지
- GeoJSON join = `dong_code`
- GeoJSON normalized 파일은 script로 재현
- Backend 실제 package 구조 유지
- 실제 데이터와 mock 데이터 명확히 분리
- AI provider는 P4 시작 전 결정
- MVP 단일 AI provider
- AI 하드코딩 답변 fallback 금지
- 실제 API 결과 기반 deterministic fallback 사용
- 과거 조율 문서와 현재 실무 문서 분리
- 작업 상태만을 위해 `작업계획.md`를 계속 수정하지 않음
- 기능별 branch + PR 방식 사용

이 문서를 Claude와 Codex의
공통 개발 기준으로 사용한다.
